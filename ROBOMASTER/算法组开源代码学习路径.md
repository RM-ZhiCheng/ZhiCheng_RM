# 算法组 · 开源代码学习路径

> 整理日期：2026-09-13
> 适用对象：算法组新人
> 素材来源： 同济 SuperPower [sp_vision_25](https://github.com/TongjiSuperPower/sp_vision_25) + 北理莫斯科北极熊 [pb2025_sentry_nav](https://github.com/SMBU-PolarBear-Robotics-Team/pb2025_sentry_nav)

---

## 0 先立两种思维

看任何开源项目，先问三个问题：

1. **它怎么跑起来的** —— 数据从哪进、经过哪些模块、从哪出
2. **它的依据是什么** —— 基于哪篇论文、哪个理论
3. **它的局限在哪** —— 依据里的假设一旦不成立，会在哪里失效

配合两种思维：

- **模块化**：分成几层、每层负责什么、层与层之间的接口是什么
- **系统化**：这些模块怎么串成一条能跑通的线

验收标准：合上代码，能在脑子里画出框架图。

选材原则：优先看生态好、用的人多的。导航就是 Nav2，生态成熟、资料多、出问题好查。
哈工大的开源很强，但结构过于复杂，不适合当入门材料——留到有判断力之后再看。

## 1 自瞄

### 1.1 分层与代码对照

| 分层 | 职责 | `sp_vision_25` 中的位置 |
|---|---|---|
| 感知层 | 拿到相机图像和时间戳 | `io/camera.cpp` |
| 特征处理层 | 从图中找出装甲板 | `detector.cpp`（传统）、`yolos/yolo11.cpp`（神经网络） |
| 坐标计算层 | 四个角点像素 → 距离 | `solver.cpp` |
| 位姿计算层 | 位置 + 姿态 → 仰角 | `solver.cpp`、`armor.cpp` |
| 运动解算与预测层 | 算 yaw/pitch、弹道解算、预测目标位置 | `tracker.cpp`、`target.cpp`、`tools/trajectory.hpp`、`aimer.cpp` |
| 通信层 | 把角度指令发给电控 | `io/cboard.cpp`、`io/serial`、`io/socketcan.hpp` |

### 1.2 阅读顺序

1. [`readme.md`](https://github.com/TongjiSuperPower/sp_vision_25)，重点第 3.4 节（软件架构）和第 4 章（轨迹视角下的自瞄理论）
2. `src/standard.cpp`，只有 83 行，是整个项目最短最完整的主流程
3. `tests/auto_aim_test.cpp`，最有用的入口：不用相机、不用机器人，直接读 `assets/demo/demo.avi` 和配套的四元数文件就能跑
4. 按需深入 `tasks/auto_aim/`，先看 `.hpp` 接口，再看 `.cpp` 实现

主流程就是六句话（`src/standard.cpp` 第 57~80 行）：

```cpp
camera.read(img, t);                    // 1 取一帧图像 + 时间戳
q = cboard.imu_at(t - 1ms);             // 2 取"拍这张图时"云台姿态四元数
detector.detect(img);                   // 3 识别：图 → 装甲板列表
tracker.track(armors, t);               // 4 估计：装甲板 → 整车运动状态
aimer.aim(targets, t, bullet_speed);    // 5 决策：目标状态 → 云台角度 + 是否开火
cboard.send(command);                   // 6 指令下发
```

两个容易忽略但很关键的点：

- 第 2 步的 `t - 1ms` 是时间对齐。图像来自相机、姿态来自电控，时间戳对不上，后面算出来的位置全是错的。
- 第 3 步和第 4 步的区别：识别器只回答"这一帧看到了几块装甲板"，估计器回答"敌方整车在怎么动"——旋转中心、角速度、朝向、各装甲板半径。只有有了整车状态，才能预测 10 秒后它转到哪。

### 1.3 两条识别路线的取舍

| 路线 | 优点 | 代价 |
|---|---|---|
| OpenCV 传统视觉 | 算得快、精度高 | 依赖光照和颜色阈值，换场地容易失效 |
| YOLO 神经网络 | 环境适应能力强 | 精度略低，推理耗时影响帧率 |

这个取舍直接决定场上调试的难度，对**哨兵和自瞄步兵**影响最大——这两者面对的环境最不可控。

### 1.4 轨迹优化与 MPC

自瞄的决策器用的是轨迹优化，理论上是 MPC（模型预测控制，非线性控制系统优化），属于高阶内容。

代码入口：`tasks/auto_aim/planner/tinympc/`，使用的是 TinyMPC 库。

值得注意的设计选择：同济把 MPC 当**求解器**用（用来找一条满足约束的可行轨迹），而不是当闭环控制器。他们试过直接拿 MPC 做闭环控制，效果不如下位机方案。这就是"看清依据才知道局限"的实例——MPC 的前提是模型准确、算力充足，条件不满足时它并不占优。

## 2 导航

导航的系统复杂度比自瞄高得多（算法数量多很多），但**调试参数反而比自瞄少，调试时间更短**。这条结论对分工有直接意义。

参考开源：[pb2025_sentry_nav](https://github.com/SMBU-PolarBear-Robotics-Team/pb2025_sentry_nav)（深圳北理莫斯科大学北极熊战队，25 赛季哨兵），已下载到 `06_开源参考/`。
它基于 ROS 2 的 [Nav2](https://github.com/ros-navigation/navigation2) 框架，结构清晰，是学导航最合适的材料。

### 2.1 分层

1. **感知层**：激光雷达高频扫描 → 回波测距 → 视野内的三维点云
2. **里程计（LIO）**：点云 + IMU → 自己在哪里、怎么动的（`point_lio`，依据 LOAM 论文）
3. **建图 / 重定位**：先建地图，之后靠地图匹配找回自己的位置（`small_gicp_relocalization`）
4. **数据处理桥**：坐标系转换、点云转激光扫描（`loam_interface`、`sensor_scan_generation`、`pointcloud_to_laserscan`）
5. **可通行性分析**：哪些地方能走、坡度多大（`terrain_analysis`、`terrain_analysis_ext`）
6. **规划与控制**：全局路径 + 局部跟踪（Nav2 全局规划器 + `pb_omni_pid_pursuit_controller`）
7. **决策**：行为树（`behavior_trees/`）

### 2.2 北极熊仓库的包清单

| 包 | 作用 |
|---|---|
| `livox_ros_driver2` | Livox mid360 雷达驱动 |
| `point_lio` | 激光惯性里程计，输出配准后的点云 |
| `loam_interface` | 把 `point_lio` 的点云从 `lidar_odom` 系转到 `odom` 系 |
| `sensor_scan_generation` | 把点云转到雷达系，并发布 `odom -> chassis` 变换 |
| `small_gicp_relocalization` | 用 small_gicp 做重定位 |
| `pointcloud_to_laserscan` | 三维点云转二维激光扫描 |
| `terrain_analysis` / `terrain_analysis_ext` | 地形分析，判断可通行性 |
| `pb_nav2_plugins` | 为 Nav2 写的自定义插件（代价地图层、行为树节点） |
| `pb_omni_pid_pursuit_controller` | 全向 PID 追踪控制器，替代 Nav2 默认控制器 |
| `fake_vel_transform` | 底盘坐标系变化时，转换 Nav2 下发的速度指令 |
| `pb_teleop_twist_joy` | 手柄遥控（底盘 + 云台） |
| `pb2025_nav_bringup` | 总启动配置：launch、config、地图、pcd、rviz、行为树 |
| `pb2025_sentry_nav` | 元包 |

### 2.3 阅读顺序

1. `README.md`：先看数据流和坐标变换那两段，理解 `lidar_odom`、`odom`、`chassis` 之间的关系
2. `pb2025_nav_bringup/launch/`：一个 launch 文件就是一张"谁在跑"的名单。先看 `rm_navigation_reality_launch.py`（实车）和 `rm_navigation_simulation_launch.py`（仿真）
3. `pb2025_nav_bringup/config/reality/nav2_params.yaml`：Nav2 的全部参数，是理解规划与控制的最快入口
4. 然后按包逐个看：每个包先读 `package.xml` 的 description 和头文件，再看 `src/`
5. 建议的深入顺序：`point_lio`（依据 LOAM 论文）→ `small_gicp_relocalization` → `terrain_analysis` → `pb_nav2_plugins` → `pb_omni_pid_pursuit_controller`

### 2.4 要掌握的 Nav2 概念

建图（SLAM Toolbox）、定位（AMCL / 重定位）、代价地图（costmap，分全局和局部）、全局规划器、局部控制器、行为树。

看代码前先把这几个概念搞清楚，否则读 launch 和 yaml 会一头雾水。

## 4 环境备忘（Ubuntu 22.04 虚拟机）

### 4.1 已安装

编译器和基础库：`g++` 11.4、`cmake` 3.22、OpenCV 4.5.4、Ceres 2.0、fmt、Eigen3、spdlog、yaml-cpp、libusb、nlohmann-json、git、can-utils、screen。
ROS：ROS 2 Humble。
OpenVINO：2024.6.0，从 Intel 官方 apt 源安装（新 C++ ABI）。

### 4.2 两个已踩过的坑

**坑一：Windows 检出的 CRLF 换行。**
在 Windows 上 `core.autocrlf=true` 会把仓库里的 LF 换成 CRLF 写到磁盘，搬到 Linux 后脚本和 launch 文件会报 `bad interpreter` 之类的错。解决：`git config --global core.autocrlf input`，或者直接用 VS Code 远程连虚拟机改代码，文件一直存在 Linux 上。

**坑二：OpenVINO 的 C++ ABI。**
OpenVINO 的 Python wheel（含清华镜像的包）是用旧 ABI（`_GLIBCXX_USE_CXX11_ABI=0`）编译的，而 Ubuntu 的 OpenCV、yaml-cpp、fmt 是新 ABI，混用会出现大量 `undefined reference` 链接错误。判断方法：`nm -D --defined-only libopenvino.so | c++filt | grep read_model`，出现 `std::__cxx11::` 才是新 ABI。
结论：**C++ 项目不要用 Python 版的 OpenVINO 包，要用 Intel 官方 apt 源里的 `libopenvino-*` 系列**，那边编译的是新 ABI。

## 5 术语速查

| 术语 | 含义 |
|---|---|
| 自瞄 | 对移动装甲板自动瞄准 + 自动火控 |
| 击杀时间 | 打死敌方单位所需时间，自瞄效果的金标准 |
| 灯条 / 装甲板 | 装甲板由两条发光灯条组成，四个角点是所有几何计算的物理基础 |
| PnP | 从已知的 3D 点和图像 2D 点求解相机位姿 |
| EKF | 扩展卡尔曼滤波，用于估计目标运动状态 |
| MPC | 模型预测控制，用优化方法求未来一段时间的最优轨迹 |
| LIO | 激光惯性里程计，点云 + IMU 推算自身运动 |
| SLAM | 同时定位与建图 |
| costmap | 代价地图，标注哪些格子能走、代价多少 |
| 行为树 | 用树状结构组织机器人决策逻辑，Nav2 用它编排导航行为 |
